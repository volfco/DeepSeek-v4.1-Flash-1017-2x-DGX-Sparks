## What the engine exposes that OpenObserve does not hold, or holds from one rank only

| What | State in OpenObserve | What would have to change |
|---|---|---|
| `tensorfold:requests_total{key,status}`: HTTP replies by API-key label and status (`server.zig:323`, every reply) | **Not stored.** The head's collector reports 373 samples a scrape (`scrape_samples_scraped`, the same after relabeling); OpenObserve holds 372 at the same timestamp (234 plain or labelled samples and 138 histogram buckets). The one sample lost matches this family with a single key and status. Where it is lost (a processor in the collector's metrics pipeline, or OpenObserve's ingest) is **not verified**: the collector's log names no rejected metric. | Read the head collector's metrics pipeline for a filter or transform that touches this name or the `key` / `status` labels, and OpenObserve's ingest errors for it. This is the only series that separates clients from each other and good replies from errors, so it is the one that would let benchmark traffic be told from client traffic without the run logs. |
| `tensorfold:process_footprint_bytes` | Not stored: the engine emits it on macOS only. | Nothing. |
| `tensorfold:joules_total` | 20 samples from 2026-11-16/17, none since: emitted only with `TF_DS_ENERGY=1`, which production does not set. It is rank 0's GPU only. | Nothing needed: DCGM's power and energy series cover both GPUs all the time (*DGX Sparks → GPU*). |
| Everything from rank 1 (the worker, `gx10-235f`) | The engine serves `/metrics` on rank 0 only. Rank 1's numbers reach OpenObserve only where rank 0 relays them with a `rank` label: the disk tier (`spill_*`, 36 families) and `kv_shard_rank_*` (12); `kv_shard_part_*` carries a `part` label. Device memory, the Engram read histogram, the request histograms and the pair gauges are rank 0's (read from the source; not verified against a rank 1 log). | An engine change if rank 1's device memory or Engram read times matter: relay them in the stats reply the way the tier counters are. |
| The worker's `tensorfold` scrape job | The worker's collector scrapes its own `localhost:8000` every 30 s and fails every time: `up{service_name="tensorfold", host_name="gx10-235f"}` has been 0 in all 33,237 samples since 2026-11-11 18:12 UTC, and each failure writes a warning that is then shipped twice (syslog and journald). | Remove the `tensorfold` job from the worker's collector configuration. Until then read `up` for the head only (*Tensorfold → Ranks, scrape & restarts*). |
| Engine state that `/metrics` does not publish | `Status.decode_tokens_per_second`, `Status.prefill_tokens_per_second`, `Status.warming` and Engram's host-side seconds (`EngramStats.host`) are in the engine's status struct but not in `render`. | An engine change (four gauges). The dashboard derives both rates from counters instead. |

The scrape interval is 30 s on both Sparks (every job), not the 60 s the notes say.

## Useful numbers that exist only as log lines

Neither log stream holds the engine's own log: 23 days of `default` (syslog, auth.log, kern.log through the filelog receiver) and `journald` contain no `done` line. The handful of matches for `tok_per_s`, `ttft_s` and the like are command lines of ssh sessions that tailscaled logs.

| Number | Where it is today | In `/metrics`? | Cheapest way into OpenObserve |
|---|---|---|---|
| Per-request `done` line: `prompt`, `cached`, `tokens`, `rounds`, `accepted/drafted`, `prefill_s`, `ttft_s`, `decode_s`, `s_per_token`, `tok_per_s`, `tokens_per_round` | engine stdout (`chat.zig:801`) | As totals only. The dashboard and part 1 rebuild per-request values from differences between scrapes, which is exact only when one request finishes in an interval. | No engine change: ship the container's stdout. Either add the engine container's JSON log file to the head collector's filelog receiver, or start the container with the journald log driver so the journald receiver already running picks it up. Keep only lines that start with `done ` (a filter processor) and parse the `key=value` pairs into fields. The line holds counts, times and a reply hash, no prompt or reply text; filtering to it keeps the rest of the engine log out. |
| `queue_s`, `restore_s`, `render_s`, `encode_s` (per request) | `done` line only | **No.** TTFT lumps them with the prompt pass, so queueing cannot be separated from a slow prefill. | The `done` line as above, or an engine change: four histograms beside `request_prefill_seconds`. |
| `thinking`, `effort`, `finish` reason, sampled or greedy | `done` line (`thinking`, `effort`, `finish`); temperature is not logged | **No.** | The `done` line, or labels on a finished-requests counter (`finish`, `thinking`). Without it live traffic cannot be conditioned on thinking or sampling. |
| Round profile: `forward_ms`, `pass_ms`, `rows_a_round`, `absorb_ms`, `enqueue_ms`, `streams_a_pass`, `prefill_ms`; GPU-clock `tail` / `wait` | `info: {"rank": 0, "profile": {...}}` lines, printed when `/metrics` is scraped and only with `TF_DS_ROUND_PROFILE=1` (suite arms; production runs with it off) | **No.** | An engine change is the clean way: counters `decode_forward_seconds_total`, `draft_pass_seconds_total`, `decode_round_rows_total`, `draft_passes_total`, so forward ms a round, pass ms and rows a round become ratio panels and the cycle model (17.9 ms + 3.6 ms a row, 4.15 ms a pass) can be checked on live traffic, including 8 streams. Without one: turn the profile on in production and ship the `info:` lines like the `done` line (they are lifetime means, so they must be differenced). The switch's cost in production is not measured here. |
| Which client sent a request | the API-key label, in `requests_total` | Yes, but the series does not reach OpenObserve (first table). | Fix the drop. |
| Engine restarts, image and switches of the running container | docker, the recipe's deploy records | No | A `tensorfold:build_info{image, commit}` gauge would let dashboards mark deploy epochs; today they come from `runs/deploy-*`. The *Ranks, scrape & restarts* tab counts restarts from counter resets. |
