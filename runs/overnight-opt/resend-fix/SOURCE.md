# Full prompt-end checkpoint diagnosis

The first stage-image trial reported full 8,192 and 8,201 prefix hits on two salts per shape. Each cold/identical pair used the same greedy request. All four output hashes differed. The original control's 6,144 hits matched in every pair. The public teacher-forced extension samples only reached 6,144 in the endstate-only arm, so those samples did not test a full-end restore. [Stage workload](../engineering02/endstate/workload.jsonl) · [Stage scoring](../engineering02/endstate/resume-score.jsonl)

The experimental endstate patch makes two corrections to checkpoint handling. In the stage source, rank 1 padded snapshots by the cache-accounting allowance as well as the actual extras. Its restore code inferred payload from total allocation. For the endstate-only settings a normal grid state therefore looked like an end state, and a full end restored from the padding before the saved bytes. The new follower record remembers the actual optional tail and end-logit offset at save. Its spill-restored records carry only the base snapshot. The second correction orders both copies of the drafter rings and final prompt logits on the nonblocking model stream which produces and consumes them. It also restores the destination slot's absorbed cursor and preserves all decoder rings when full ends are configured. The fixes were bundled. The measured trajectory alone cannot apportion the observed error between them. [Candidate patch](candidate.patch) · [Follower layout test](layout-test.log) · [Model dispatch test](stream-test.zig) · [Dispatch result](stream-test.log)

On the repaired `5fc92d21fbf5` benchmark image, all four original 8,192/8,201 resends matched the cold run's 128-token server hash. First-token latency was 5.6–11.5 ms at these sizes. A 100,009-token resend matched at 17.5 ms against a 48.52 s cold request. Four 256-token teacher-forced continuations matched every reported score field at verified 8,201-token cuts, alongside the armed 39-case gate. Both ranks returned to the original production recipe. Odd-length append failure has a separate cause. The original tail policy selected a full 8,201 checkpoint for the next prompt of 8,458. The ratio-two KV compressor refuses an odd start because its first compressed pair would need the preceding raw activation. The native layer maps that refusal to a generic TP-world error even with a supported two-rank deployment. The separate selector change retains a full identical odd hit and uses an earlier eligible checkpoint for its extension. Even full ends still qualify for an appended turn. The selector test checks all three cases. Moving an odd checkpoint between extents has its own ratio-alignment requirement and can fall back to full recomputation if another stream holds the source. [Tail selector patch](tail-start.patch) · [Selector result](tail-start-test.log)

The host checks exercise snapshot layout, real model-copy dispatch, and the lane selector. The GPU gate is responsible for output equivalence, real cache cuts and latency. To reproduce the host checks, apply the two patches in that order to the isolated odds image source with the prior resume fixes. Run `ZIG=/path/to/zig bash runs/overnight-opt/resend-fix/host-check.sh /path/to/that/checkout` with the repository's Zig toolchain.

The separate tail image fixed the observed odd append. The 8,201→8,458 extension fell back to 8,192 and matched cold, and the aligned 8,192→8,449 extension matched at a full 8,192 hit. The even off-grid 8,202→8,459 extension reused 8,202 at 0.452 s against 4.409 s cold but produced a different 128-token greedy hash. All three identical resends matched. The gate therefore stopped before the long and concurrent cases. The 8,202 seed computes ten encoder rows after the grid boundary, followed by 257 on extension, whereas the cold longer request computes 267 rows together. The model has a short-ring attention path at 16 rows or fewer and row-dependent linear dispatch. This establishes a changed execution path. A cold no-cache run with the existing `TF_DS_DEBUG_SPLIT=8202` and equal token IDs could test whether that split alone reproduces the difference. ## Memory and row retention with two full ends

Both ranks' deployed model configs have SHA-256 `4eac47f0da99a65f2bcfb97ca357f7d5388a79c9b377d6dd65b1ed18548d846d`. Both keep the complete last-token logits after a TP gather. The per-rank snapshot payload is the same on head and follower. [Immutable geometry](model-geometry.json) · [Byte calculation and log check](memory.py) · [Results](memory.json)

| Snapshot payload | Bytes per entry per rank |
|---|---:|
| 40 model rings, 144 rows × 512 bf16 values | 5,898,240 |
| 3 ratio-two layers' raw KV and gate, 64 × 512 float values per buffer | 786,432 |
| Ordinary snapshot payload | 6,684,672 |
| 3 DSpark rings, 144 × 512 bf16 values | 442,368 |
| Full 129,280 float logits | 517,120 |
| Full-end snapshot payload | 7,644,160 |

Two full ends contain **14.580 MiB per rank**, of which 1.830 MiB is specific to the drafter rings and logits. The pair holds 29.160 MiB. A newly inserted third full end can briefly make this 21.870 MiB/rank before the oldest full entry is dropped. The two-entry rule counts full ends by insertion order across the head store, including distinct sessions. Ordinary grid entries and restore destinations use the common 512 MiB budget. This path reserves the worst-case 7.290 MiB per entry, including every ordinary grid entry, although the repaired follower and head allocate only 6.375 MiB of device payload for a regular grid checkpoint. A pure resident set's theoretical ceiling falls from 80 ordinary entries with the switch off to 70 charged entries with it on. A full budget can also evict an ordinary state before the independent oldest-end rule runs. All twenty observed ledger lines (up to sixteen resident states) in the original arm's head log agree with the byte formula rounded down to MiB. Allocator granularity and metadata are outside those payload values. [Head ledger](../engineering02/endstate/rank0.log) · [Verified capacity](memory.json)

The additional retention has two other components. At keep time the head copies the token IDs twice, approximately eight host bytes per prompt token outside this device budget. The second copy follows the most recently resumed prompt and can grow on an extension. The follower uses the head-managed checkpoint ID and stores its local payload. The sharded planner preserves the prefix's existing compressed rows until eviction, with shared prefixes counting once within the same extent. For each even token pair the KV owner has 1,440 bytes of compressed codes/scales for the four KV source layers, plus 340 bytes of replicated index codes/scales on **each** rank. A separate 300,000-token prefix therefore occupies **267,000,000 bytes on its owner** and **51,000,000 on its peer** within already allocated planes. If that extent already had a 299,008 grid state, the additional 992 rows amount to 882,880 owner bytes and 168,640 peer bytes. Keeping the full end creates no dedicated GPU allocation for those compressed rows. An identical full-end state is memory-only and skips the durable-tier write. This accounting alone cannot predict hit-rate loss under real queue and cache pressure. [Computed depths](memory.json)

## Experimental snapshot accounting

The isolated charging patch lets a family report the live-save payload for a specific prompt length before the store filters, reserves or saves the requested checkpoint. DSV41 reports 6,684,672 bytes for an ordinary endstate-mode grid save or durable restore and 7,644,160 for a full end. In combined exact-resume mode, the follower still allocates a tail for every non-full live keep; the estimate covers the larger rank’s allocation. The existing durable DSV41 tier returns zero destination-size hints at lookup and adoption, including pre-existing points. Its context-free estimate now reserves the base destination size. Other families retain their previous estimate. No rank-wire or stored format changes are required. [Isolated patch](charge.patch)

In the actual store’s host test, the original uniform reservation retained only 70 of 80 offered entries. With contextual charging the same store retained all 78 ordinary states and two full ends at **536,692,736 bytes**, leaving 178,176 bytes inside 512 MiB. The charge change restores the theoretical maximum of 80 in this layout. It preserves the existing eviction policy, including the generic budget check before replacing an old full end. A full cache may still shed an ordinary entry during replacement. The test separately exercised planned mark prefiltering and pre-pass eviction, an in-flight disk restore competing with a full save, and equal head/follower sizes derived from the real model. The 70-test store suite and three focused model-module tests passed under ReleaseSafe. Both AArch64 engine binaries cross-built off-pair. No live deployment, hit-rate improvement or throughput measurement is part of this result. ## Observed exact-resend opportunities

The November 13 external-only cohort completed 652 requests at 643 distinct prompt lengths. Only nine requests had the same length as an earlier observed request. The nine used 7.2 seconds of the cohort's 2,549.7 total prefill seconds. Even if their token IDs were identical, the corresponding full end survived and restore were free, they therefore account for **at most 0.283%** of in-cohort prefill time. Only two of 619 requests at or above 8,192 tokens had an earlier equal length. Each of the 409 requests at or above 100K, including all 80 at or above 250K, had a unique length in the entire window. No request matched the length of either of its two immediate predecessors when ordered by estimated first token. That last comparison is descriptive because entry replacement follows successful saves. It cannot identify the exact resident set. The same window had 657 post-prefill cache ledger samples. All matched the 6.375 MiB ordinary payload and 512 MiB budget. **560 samples held more than 70 entries**, and 549 held 78–80. The repaired policy’s slot reduction would have affected the capacity available in this traffic mix. From the preceding ledger at 07:09:23 UTC through 15:57:56 the head added 638 memory-cache hits, 23 misses, **270 evictions**, zero refused keeps and zero failures, with no counter resets. The 270 evictions occurred across 256 ledger intervals. The store increments this counter while reserving future marks or restore destinations as well as while making room for an immediate keep. All ended above 70 states, and 267 evictions appeared in intervals ending at 78–80. Strictly differencing the first and last in-window lines yields 22 misses because the first sample already includes a new miss. The 661 lookup events and 652 completed requests have different denominators. With ordinary trim alone, 20 rings plus the raw stores cost 3,735,552 bytes per checkpoint (143 slots). The archive identifies neither the displaced entries nor their subsequent reuse, so it cannot establish how many misses a higher ordinary capacity would prevent. The cohort excludes unknown state already resident when the window opened and requests missing from the archive. Equal length is a necessary condition for an identical resend. The archive provides no content-match guarantee. The full-end-only optimization therefore has a clear application to a declared repeated-prompt workload and little opportunity in this observed chat interval.
