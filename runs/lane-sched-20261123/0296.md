(0.39 ms/forward on the critical path, `runs/trace-review-20261123/RESULTS.md` §4) against a 0.22–0.32

32K and 128K, brief the decode union fetch behind a switch.

## Semantics (the decisions inside the item's wording)

- **"by depth" = the round's context depth**: the round's context bucket (`round.bucketFor`, the depth
  quantization the codebase already keys graphs on), in floor-log2 bands. Rationale: §4's unknown is
  "how much the pick sets overlap **at depth**", the gate is "at 32K and 128K" (context depths), and the
  repo's recipes use "decode at that depth" for context depth. A band's `depth` label is its lower bound
  (2^i), so `bucketFor`'s exact powers of two land on the label: 32K → 32768, 128K → 131072.
  `TF_DS_IDX_BUCKET_FINER`'s finer buckets land in the power-of-two band below their value (noted in the
  `bandOf` comment; the band is a floor-log2, so a 30,000-row bucket reports at depth 16384).
- **"per fetch" = per actual fetch**: each decode fetch that packs/exchanges picks counts once —
  `fetchDecode` (after the `TF_DS_KV_FETCH_REUSE` early return, so reuse-skipped layers do not count),
  `ownerDecode`'s and `ownerRing`'s fetches. A fetch of a selection counted already in the round (a run's
  later layers: the same `FetchKey` = (kv source, index layer, kk)) copies the fresh count instead of
  recounting; the per-fetch accounting (`fetches`, `picks = rows × kk`) stays exact either way.
- **The count is the prompt union's own**: `shard_ops.unionCount` (the `shard.UnionRef` host model —
  the same kernels the prompt union fetch ships) marks the first `kk` picks of every window row in the
  prompt fetch's own marks buffer (`ch.sf_cum`), scans, and leaves the count in `ch.sf_sums`. The marks
  are zeroed in the stream's order per fresh count. **The count stays on the device** (a 4-byte DtoD per
  fetch into the per-layer slot; §4's own requirement: "the ring's row kernels already send a
  device-listed count" — this is that pattern), read back once a round after the round's own sync like
  the ring probes. Graph-safe: the per-fetch copies are captured nodes over stable buffers; the tally
  reads whatever the replay wrote.
- **One line a run, cumulative**: `{"rank": 0, "kv_pick_union": {"fetches", "picks", "distinct",
  "by_depth": [{"depth", "fetches", "picks", "distinct"}, ...]}}`, never reset (the profile line's
  convention: readers take deltas between scrapes). `picks` = `rows × kk` summed over fetches (what
  every-pick fetching sends today, in pick units); `distinct` = the union's rows summed per fetch (what a
  union fetch would carry). The gate number is `distinct / picks`.

## Open decisions

- **"by depth" reading** (this run's interpretation): depth = the round's context depth (bucket bands).
  The alternative readings of the item wording were: depth = the pick's context-depth band (how deep each
  pick reaches), depth = the window row's depth (union growth as rows are added), depth = the layer depth
  of the fetch. Chosen reading matches §4's "at depth" against "below 512 compressed rows of context they
  are identical" and the "at 32K/128K" gate. If the operator wanted per-pick depth bands instead, the
  tally's band source changes (the marks' prefix counts already give per-range distinct for free —
  `cum[hi-1] - cum[lo-1]` in `shard.UnionRef`'s scan) — a small follow-up, not a rewrite.
- (Carried from 0293/0294, unchanged): the full stage-row clamp (option B) stays operator-declined;
  0293/0294 must be measured apart.
