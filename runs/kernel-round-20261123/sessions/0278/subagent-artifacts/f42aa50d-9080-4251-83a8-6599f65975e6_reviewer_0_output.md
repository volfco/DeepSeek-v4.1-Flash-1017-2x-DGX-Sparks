### 2. On-path correctness — no issues found

- **Correct** — The kernel writes `out[r * os + d]`, `d < D`, with `out` a bf16 pointer, so `os` is in **elements** (dsv41_torch.cu:262-278); the wrapper passes `os` as `c_longlong` elements (exact.zig:395-406). The on-path call (prompt.zig:2699) gives `out = ch.taps + j*D·2` bytes and `os = ntaps·D` elements, landing tap j's row i col k at element `i·ntaps·D + j·D + k` — exactly `packedElem` (taps_packed.zig:37).
- **Correct** — That is precisely where the dropped `copyRows` placed bytes: dst `dr.at + j*d*2`, dst stride `dr.taps_w*2`, width `d*2`, `ch.n` rows (layer_main.zig:725 etc.; `copyRows` semantics at ops.zig:588-591: `bytes`-wide rows into stride-separated rows) with `dr.taps_w = ntaps*D` (draft.zig:252, 363). The layout-equivalence test in taps_packed.zig:45-63 encodes this.
- **Correct** — Matches the already-packed decode write `tri_basic.tap(t, h, rd.taps + ntap * d * 2, c.dspark_taps.slice().len * d, R, d)` (round.zig:2129, `os` semantics per tri_basic.zig:43-45) element for element.
- **Correct** — Drafter reads hold: `absorb`'s rows are contiguous `[n, taps*D]` (draft.zig:491-507: offsets `taps + (n-keep)·taps_w·2` bytes), `absorbMany`→`mainKeys(dr.at, n)` (draft.zig:522, 533), `grouped` takes element stride `dr.taps_w` (draft.zig:544). Under the switch `ch.taps`'s first `ch.n` rows are contiguous `[n, taps*D]` — same bytes `dr.at` held. Buffer sizing is safe: allocation `max(ntaps,1)·cap·D·2` bytes (prompt.zig:616) vs packed extent `ch.n·ntaps·D·2`, with `ch.n ≤ cap` enforced (prompt.zig:972 `ChunkTooLong`, prompt.zig:2655).

**Finding 2.1 — P2 (report-only)** — If a future checkpoint put a tap layer **below `c.layers/2`** while `replayCut` grows `ch.n` mid-chunk (prompt.zig:2648-2666, only under TF_DS_EXACT_RESUME tail-prepend), taps written before the cut would leave rows `[old_n, new_n)` stale in both layouts — but *different* stale bytes (previous planar rows vs previous packed rows), so on/off would diverge there.
