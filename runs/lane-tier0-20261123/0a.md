## Verdict

The divergent patch is **0206 alone** (the key fold). Mechanism, proven host-side:

- The kit's `_score_keys` writes keys that order as **signed** i64 (torch.topk on int64 — the kit step
  `tri_index.TopK` wraps; production's picks are the kit's, so the fused `_topk_sel` that replaces it must match).
- The fused key fold (0206) writes `scoreKey`'s encoding instead, which differs in **exactly the top bit** (measured
  in `runs/fused-followup-20261121/RESULTS.md`: score 0.0, column 0 → kit `0x00000000ffffffff`, engine
  `0x80000000ffffffff`; same low word / ordered bits on all 64 probe columns) and orders as **unsigned** (the fused
  pool's radix-select order — that is why `scoreKey` flips the bit at all).
- The fold writes that encoding into `rd.keys` / `rd.tmax` and skips the kit's `_score_keys` (parked 0206's
  `keys_done`). `topk_select_pruned` / `topkSelect` then read it with a signed compare, which **reverses every
  negative-score vs non-negative-score pair** and preserves each class's own order. The pruned picks therefore agree
  inside one sign class and diverge whenever both classes meet at the selection boundary — the four mismatches'
  signature (completion length + token hash), and why the fold's byte parity ("identical modulo the flip") missed it.
- Counter-evidence resolved: if the consumer compared unsigned, the folded keys would be correct and *no* case could
  diverge — the observed 4/39 divergence is itself proof the consumer is signed on this buffer.
- **Width boundary** (the failing window 16,384 < width ≤ 65,536):
  - Floor **16,384** = `candidate_blocks * candidate_block` (2048 × 8, `config.zig:266`): below it the
    candidate-source arm takes `candFast` (no pool, no fold) and the keys still come from the kit's `_score_keys`
    (`round.zig:1328` gate, `:1368/:1371` kit writers). Hard code gate, both trees.
  - Ceiling **65,536** = the follow-up tree's fused-pool coverage: 8,192 blocks × 8 ("the old cap is inside the new
    one", `idx_fused.zig`'s `fuseOk` test). Above it the unfused sequence runs and `_score_keys` writes the keys.
    (Alternate reading: the follow-up tree's small-row arm diverts there — the two cannot be told apart statically;
    0297's `key_profile` line settles it on the window.)
  - Both fold gates also need `cb == 8` and the `.idx_fused` arm (parked 0206's `keys_done = cb ==
    idx_fused.key_fold_bsize`).
- **`len_100000` reconciles**: its width is past 65,536, outside the follow-up tree's fused pool, so the kit's
  `_score_keys` wrote its keys and the picks matched. All four failing lengths land inside the window; every matching
  shorter case lands below the floor (the len→width map is consistent with `width == len`; 0297's record pins the
  exact widths).
- **Adoption warning**: this tree (post-0217) has `max_nbk = 16,384` blocks = 131,072 columns. Adopting parked 0206
  **as-is** widens the divergence window to 16,384 < width ≤ 131,072 — `len_100000` would diverge too. 0298's fix is
  a prerequisite for adopting 0206 at all.

## Host-side localization (the step-1 check)

`zig/src/families/dsv41/idx_fused.zig` (in 0297), CPU emulation of both producers and the one consumer:
fold keys (`scoreKey`) + unsigned tile maxima vs kit keys (`scoreKey ^ 0x8000…`) + signed tile maxima, through a
`topk_select_pruned` miniature (k best 64-key tiles by signed tmax, then k largest keys as signed — or the direct
top-k below `prunes()`'s bound, `tri_index.zig:144`), at widths 16,384 / 20,000 / 30,000 / 32,768 / 50,000 / 64,000 /
65,536 (the four lengths' shapes + the window edges), k = 512 (`index_topk`), on adversarial rows: mixed-sign tiles,
all-negative (with -inf, ties), all-non-negative (with ±0 ties, +inf), NaN. Result: **mixed rows diverge at every
width, and the picks split by sign class** (kit takes the non-negative scores incl. NaN, fold takes the negative
class); **single-class rows are identical at every width**. That is exactly the observed failure shape.
